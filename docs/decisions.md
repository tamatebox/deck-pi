# Decisions

Design settled 2026-09-09. The reasoning, which does not expire when a module
lands. `README.md` carries what is built.

**Each row is a ruling.** Reasoning is here only where someone would otherwise
re-derive the opposite; elsewhere the ruling is its own argument. Findings that
constrain code live in that code's doc comments instead, which is nearer the reader
who needs them — `src/media.rs` for the volume UUID and the mount test,
`src/cue.rs` for path escaping, `src/input.rs` for the clock, `src/file.rs` for the
shift.

## Settled

| Decision | Why |
|---|---|
| Raspberry Pi 3B+ | Already owned. Same footprint and header as a 3B, so nothing in the board stack depends on which it is. |
| One Pi per deck | Per-track rate switching is then free — reopening this deck's DDC cannot interrupt a different machine. |
| Digi2 Pro + IsolatorPi III | Dual oscillators in master mode take the Pi's PLL out of the clock path; the isolator keeps Pi ground noise off the audio boards and gives the controls a non-isolated header. |
| Separate clean supply on J1 | The isolation is only real if the audio side is powered independently. 5 V, not J1's 3.3 V floor: the rail passes through to a 5 V HAT. |
| Fit the isolator last, not first | The manual (§J-1) says prove audio *before* inserting it. A direct-mounted Digi2 Pro runs the whole v1 software stack — but is not an audio-quality baseline. |
| WAV / AIFF sources only | Uncompressed, so no decoder ever runs on the Pi. RF64 and Wave64 come free with libsndfile and lift the 2 GiB container ceiling. |
| Native rate and depth per track | Upsampling costs disk and CPU and buys nothing. Matching rates is also what makes bit-perfect possible. |
| Locked int32 ring around the playhead | Decouples track length **and** sample rate from RAM — cost is constant in both. Was mmap + mlock; see Reversed. |
| The window's two halves are relative to the **direction of travel** | Not to increasing frame number: an append-only ring accumulates for free only on the side the playhead has passed. A forward-only refill served a descending playhead **0 of 12 periods**, measured. Direction comes from successive playhead values, so nothing new is plumbed, and an explicit seek clears it. Costs one missed period per relocation — reverse playback is served, not gapless. |
| Wireless off, Ethernet only | Fewer interrupts, and the 3B+ radio is dual-band, so this removes a 5 GHz transmitter too. Confirm wired access *before* disabling. |
| Buttons and encoders on GPIO, kernel-decoded | No MIDI jitter, no USB polling interval. Never userspace polling. |
| No LEDs | Keeps the wiring simple. Not a noise decision — a statically driven LED is DC and quieter than the display. The display shows state instead, and can show *why*. |
| Everything in Rust, one process | v1 would be comfortable in Python but v2 would not. The split then collapsed anyway: the browser needs libsndfile too, so a language boundary would mean binding it twice. `embedded-graphics` also gives the device-swap reversibility that kept the UI in Python. |
| The realtime setup is applied **and read back**, in `src/rt.rs` | `mlockall`, `SCHED_FIFO` and core pinning are properties of the process, not the code, so no test reaches them — and all three fail silently with audio still coming out. Each is verified against the kernel's own view, and two are answered up front from `getrlimit` so a failure prints the missing `limits.conf` line. The pre-fault measures its own reach, the first version having touched one page. |
| **Fence when a fence costs no test surface; nudge — in words — when it would** | Recorded because one day produced both dispositions and either alone generalises wrongly. `CueStore::set` stayed public with a note that says it is load-bearing, because narrowing it would cost the store its own tests; `no_alloc` moved into the crate because that fence was free. The question is what the fence costs, not which is safer in the abstract. |
| Enforce the callback rules with `assert_no_alloc` | A global allocator wrapper that fails loudly is what turns the discipline from intent into something checked. **Scope correction, measured:** it wraps Rust's `GlobalAlloc`, so a C library calling glibc is invisible to it — which is nothing for libsndfile in the window thread and everything for libsoxr in v2's callback. |
| Read files through a hand-written libsndfile FFI | About forty lines of `extern "C"`. The binding crates stopped moving in 2021; at this size owning the declarations is sturdier and auditable. `symphonia` cannot be used — no RF64 or Wave64. |
| Output format is `S24_LE`, and the ring matches it | Read from kernel source rather than waiting for hardware: `WM8804_FORMATS` offers no `S32_LE`, so the intersection with `bcm2835-i2s` is `S16_LE / S24_LE`. Right-aligned in a 32-bit word, so the ring holds `sf_readf_int`'s value shifted right 8, done off the deadline. Still a pure shift. |
| GPIO 5 is the 44.1 kHz crystal, GPIO 6 the 48 kHz one | Reassigning them does not merely break oscillator select: the driver falls back to a 27 MHz sysclk, which is the WM8804's **PLL** reference, so audio keeps playing through the high-jitter path the build exists to avoid. |
| `sf_readf_int` supplies the ring | Its convention puts the source MSB at the destination MSB, so the byte swap and the 24-bit unpack are not our code at all. The only thing added is the right-8 shift. |
| Format scope is exactly the DDC's limit | 44.1 / 88.2 / 176.4 and 48 / 96 / 192 kHz, int16 and int24 only. Nothing separate to remember: if the Digi2 Pro can send it, the deck plays it. |
| Every supported conversion is a pure shift | Nothing is rounded, scaled or truncated anywhere. Excluding 32-bit is what buys this — float32 needs a clipping or scaling decision, and scaling would be a gain stage. |
| The window is sized in **bytes**, not seconds | `min(60 s, N MiB)` keeps RAM constant across all six rates. N is **not only a jog-feel parameter**: the forward half is also how long playback survives a knocked connector. At 64 MiB that is 60 s at 48/24 but 21 s at 192/24 — see [#9](https://github.com/tamatebox/deck-pi/issues/9). |
| **exFAT and HFS+, both from v1** | The criterion is native read-write on macOS *and* a mature in-tree Linux driver. Supporting both costs nothing, mounting being a udev concern at a fixed path. FAT32 is out on the 4 GiB file limit, which bites a 192/24 track at 31 minutes; ext4 because the preparing machine cannot write it cleanly. |
| Journaled HFS+ mounting read-only is a feature here | The driver forces `SB_RDONLY` and offers `force` at your own risk. That is already the policy for removable media, so the restriction and the requirement are the same thing. Never pass `force`. |
| Do **not** pass `nodecompose` on an HFS+ mount | The driver composes filenames on the way out by default, so Japanese names arrive precomposed and no normalisation pass is needed. Pass it and every dakuten becomes a second code point. |
| APFS is the one still requiring out-of-tree code | Not in `fs/`, so it would mean FUSE or a module rebuilt per kernel update, both reverse-engineered, neither able to read FileVault. Moot: the drive is HFS+. If it ever matters, the fixed-path design means a driver plus one udev branch and zero lines of Rust. |
| Treat the mount as fallible, but do not design around it | Removal is the dominant case. The two other paths — USB re-enumeration after a power dip, and a bumped connector in a venue — do not change the code: `read_dir` returns a `Result`, so the requirement amounts to "do not `unwrap()`". The audio side already survives it. |
| What the DAC accepts is out of scope | S/PDIF is unidirectional, so a DAC that cannot lock goes silent and the software can never detect it. A configurable ceiling was proposed twice and dropped twice: the deck cannot tell which DAC is attached, so it would be a claim, and a stale claim sounds certain while being wrong. |
| The UI distinguishes "no stick" from "stick I cannot read" | Showing only `No USB` makes a formatting mismatch look like broken hardware. Say *why*, not just *that*. |
| A udev rule calls `systemd-mount`, at a **fixed path** | Nothing mounts removable media on a headless box. `systemd-mount` creates a transient unit, so teardown on removal is automatic where a direct `mount` would leave it unowned. It also keeps mount privilege out of the audio process, which needs no root at all. |
| Match on `ID_FS_TYPE`, not "the first block device" | A Mac drive with a GUID partition map carries a vfat EFI partition, so taking `sda1` would mount that instead of the music. Matching the two filesystems does partition selection as a side effect — and is needed anyway, since they take different option names. |
| The fixed mount point is what enforces "one stick" | A second volume finds the path occupied and does not mount, so "the first one only" falls out of path uniqueness instead of needing selection logic. |
| `--automount=no`, explicitly | Automount is implied for removable devices and makes the mount point exist whether or not media is present, destroying the simplest presence test. **But "one `stat`" was too strong, and this row used to say it** — see below. |
| Presence is `st_dev` against the parent's, **not existence** | Correcting the row above, found while building `src/media.rs`. An existence test additionally assumes systemd *removes* the directory on unmount, and a failed unit, a crash or a stray `mkdir` leaves it behind — reporting a stick that is not there, a third way to confuse the two states this design exists to tell apart. Measured; the numbers are in `src/media.rs`. |
| Ownership comes from mount options on both filesystems | exFAT has no POSIX ownership; HFS+ carries the preparing Mac's uids. Either way `uid=`/`gid=` decide who can read, and getting them wrong means the mount succeeds while the application reads nothing. Numeric only — the kernel resolves no names. Exact option lists are in `implementation.md`, read from the drivers. |
| The medium is solid-state — never a spinning disk | Recorded so spin-up current, first-access latency and scattered seeks are not re-derived as concerns. The worst case the window thread asks for is 1.5 MB/s, at 192/24, so sustained read is a non-question either way. |
| The cue key's volume UUID comes from `blkid`, not from the mount | Neither filesystem exposes its serial through a file API, and the two formats differ, so store it as an opaque string rather than parsing it. **Corrected: this row used to describe HFS+'s shape wrongly** — the raw volume id never appears, `libblkid` hashing it first. The error was harmless because the value is only ever stored and compared, which is also why two tests asserting contradictory shapes both passed. Implemented with no subprocess; the mechanism is in `src/media.rs`. |
| **No volume UUID is a browsable state, not a failure** | The stick browses and plays; what it loses is the cue store's key. Encoded in the type (`Browsable { uuid: Option<String> }`) rather than left to a caller to remember, because a silently non-persisting cue button is worse than one that explains itself. |
| **Two byte-identical sticks sharing their cues is correct, not a collision** | Raised by review and recorded as *not* a defect, so it is not re-found and filed as work. A clone should behave like the stick it copies, and the fixed mount point means only one can be mounted at a time. |
| One stick, the first one, mounted read-only | A stick pulled mid-set cannot corrupt the filesystem, and there are no dirty pages to write back. |
| Dotfiles are hidden, and on this medium that is **not cosmetic** | Found while building the browser. A Mac-prepared stick carries `._name` AppleDouble twins, and `._piece.wav` would sit directly beside `piece.wav` reading as a broken duplicate of it. Note this is the *only* filter: an unplayable file is still shown, marked, with the reason, because hiding refusals would make a folder of FLAC look empty. |
| Folders first, then files; each group in **natural** order | `readdir` order is neither stable nor meaningful, so some order had to be imposed. Folders first matters more than usual here: with two browsable rows on the smallest candidate panel, collecting the navigable rows at the top is the difference between seeing a folder and scrolling to find it. Numeric-aware, which costs nothing on unnumbered names, so no assumption about the material is involved. The tie-break on raw bytes makes the order **total**, without which a reload could reshuffle rows under the selection. |
| The selection does not wrap at either end | A detented encoder gives no feedback that a list ended, and on a two-row panel wrapping is indistinguishable from a mis-scroll. A CDJ's list does wrap, so this is a deliberate departure and the reason is the row count. |
| Header reads are driven by renders, not by encoder events | Redraws are already coalesced to 30-50 ms, so only rendered positions need headers and a fast spin's intermediate ones are skipped. The redraw budget bounds the read load and no second timer is needed. |
| Cache header reads by path, and read the whole visible page | The cache is what makes it cheap rather than the debounce: scrolling one row leaves every other visible row already read. **The figures were first sized against sixteen rows, which is no candidate in [#2](https://github.com/tamatebox/deck-pi/issues/2)** — those give four to thirteen. The conclusion survived the correction; the arithmetic did not, and a wrong number supporting a right conclusion is what gets re-derived later. |
| **Three input disciplines, not one** | BACK, PLAY/PAUSE and ENTER fire on key-down, where latency is felt. CUE emits press *and* release because the Cue Point Sampler continues while held and so cannot wait for a threshold. Only FF and REW get tap-versus-hold, because only they carry two meanings. **A uniform rule would be simpler and wrong: PLAY held slightly long would emit a hold and never a tap, so the deck would not start.** |
| The hold threshold is timed from a **monotonic read**, not the event's timestamp | Using the event's is the obvious thing and it is wrong: kernel input timestamps are `CLOCK_REALTIME` by default, so an NTP step — plausible with the maintenance cable in — turns a tap into a forty-minute hold. Taking the time as an argument is also what makes tap-versus-hold testable with no device and no sleeping. |
| The encoder's axis type is **not** assumed | The overlay reports relative or absolute depending on a parameter, so both are handled and the code does not depend on a line of `config.txt` nobody has run yet. The absolute flavour needs one extra rule: the first reading sets a baseline and emits nothing, or an encoder starting anywhere but zero scrolls that far on its first event. |
| Cue points live on the Pi, not the stick | Keyed by volume UUID plus relative path. The stick is content; the Pi owns state it created. Consequence: cues would not travel between two decks. |
| The cue file is hand-written, line-based, and **escapes the path** | The whole need is a map from a path to a `u64`, smaller than the crate that would read it, and a format you can `cat` is worth having on an appliance you SSH into. **What decides the format is that a filename can contain a newline** — verified as a real HFS+ filename — so a naive `frame<TAB>path` line is not untidy but wrong. |
| The cue key is **raw bytes**, not a `String` | A lossy conversion maps every invalid sequence to the same replacement character, so two different broken names would collide on one cue — silently, and only on the medium that produced them. |
| Setting a cue **writes through, atomically** | A deck gets switched off at the wall, so flushing on shutdown would routinely lose the last thing set. Atomic because a power cut mid-write would otherwise lose *every* cue for that stick rather than one. Sorted, so re-saving is byte-identical and a diff shows what changed. |
| State lives in `$XDG_STATE_HOME/deck-pi`, one file per volume | State, not config or cache: the deck created it and cannot regenerate it. One file per volume means dropping a stick you no longer use is deleting one file. A volume name that cannot be a filename is **refused, not sanitised** — mangling two names into one file would merge their cues. |
| CUE follows the CDJ-350, and there is no separate STOP | Read out of the manual rather than recalled. Paused, CUE **sets**; playing, it **returns** and pauses; held at the point, it **plays while held**. The finding that matters: a CDJ has no STOP, because returning to the cue point and pausing *is* stopping — so the hold gesture is free for preview instead of being spent on a stop the transport already has. Costs no new mechanism. |
| **Loading a track waits at frame zero, not at its stored cue** | Settled by the user, and surveyed rather than assumed because the reference player has no answer — the CDJ-350 does not persist cues at all. Where stored cues do exist, both behaviours are real and **jumping is the opt-in one**, so frame zero is the professional default. **The cost is named rather than hidden:** with the playhead at zero and a cue elsewhere, the first CUE press overwrites the stored point — specified behaviour, on a position the operator did not choose, and the most likely first gesture after a load. Not to be fixed by special-casing: a mode that exists only just after a load is invisible in the code and unlearnable at the panel. |
| Auto cue is not adopted | The CDJ-350 skips the silent lead-in and places the cue where sound starts. **The rejection stands but not its original framing**, which split club from quiet material — the deck plays both. It stands on the quiet case alone: one piece that opens below the threshold deliberately is enough to make an automatic decision wrong, and a rule has to be right for everything on the stick. |
| **An FF/REW tap loads the next track and waits at its head** | Settled by the user, and **a departure from the CDJ-350, whose opposite the first version of this row claimed from memory.** Shares one rule with the row below rather than being two that could drift: **nothing starts making sound that PLAY did not start.** One consequence the software leans on — a track change therefore always contains a pause, which is what lets the threads and sink be per-track and every drop happen off the deadline. |
| **A deck with nothing loaded refuses every control, and the transport enforces it** | Not the dispatch, because two copies of a state machine's rule is how two orders drift. **This is a consequence of `Stopped` becoming reachable**: while it was constructed and never stored, nothing that read the state could be wrong, so the guard was not merely absent but unnecessary. Found by a hang rather than a failure — `AtEnd::Stop` means a caller that plays without loading loops on `Paused` for ever. |
| **The threads and the sink live as long as the track is *loaded*, not as long as it is *playing*** | The natural reading is the other one and the first version took it. Then PAUSE would tear down an ALSA device and a 64 MiB ring mid-set, and a deck on the last frame could not be cued back into. What ends a run is unloading, the medium going, or a fault. Affordable **only because a track change always contains a pause**. |
| A track that reaches its end stops | Nothing starts on its own. In a venue, a next track beginning while attention is elsewhere is worse than a silence, and PLAY is right there. Auto-advance is a small addition later if wanted. |
| Raspberry Pi OS Lite (64-bit) is the base | Four constraints already pin it: the HiFiBerry overlay and machine driver live in the **downstream** tree; the mount design commits to `systemd-mount`; `config.txt` on the FAT partition is what makes a bad setting recoverable by reading the card on a Mac; and exfat and hfsplus must be in-tree. 64-bit is just the current default. |
| **The v2 ADC is on I2C, which is what chose the display** | One unresolved part decided the fader's ADC, the panel, and the button count. Settled by a **usage answer, not arithmetic**: the I2C branch offers twelve buttons with a small panel *or* eight with an SPI panel, and twelve is only worth having if four more controls are wanted — they are not. So the branch that spends those pins on the panel wins with nothing given up, and the part is better on merit anyway. **Two corrections came out of settling it.** An earlier table paired the I2C ADC with the larger panel *and* twelve buttons, spending the same four pins twice — **freeing SPI0 is not leaving it empty.** And the tally then balances at **zero spare**, which promotes two properties of an unbought panel to load-bearing; [#2](https://github.com/tamatebox/deck-pi/issues/2) holds them. |
| **A part you own is a fact; a part you might buy is a constraint** | Written down because the line was being crossed. `WM8804` and `CA-IS376x` are named by number because they are on the bench. An unbought component gets its *requirement* recorded instead — a catalogue number there turns a purchase into a design premise. The same reframing made a temperature finding stronger: not "this series is rated to +50 °C", but **an enclosure hot enough to throttle the Pi at 60 °C is already outside a commodity panel component's rating**, which survives any substitution — [#6](https://github.com/tamatebox/deck-pi/issues/6). |
| FF / REW are a silent seek in v1 | An audible scan needs the resampler, which would give v1 a second mode and break "unconditionally bit-perfect". In v2 it becomes `r = 4` on the existing rate variable — no new mechanism. |

## Reversed during design

Recorded because the superseded reasoning is plausible enough to be re-derived by
accident. This section is the one thing in this file with no other home.

| Was | Now | Why it flipped |
|---|---|---|
| Unify the library at 96 kHz to keep the resample ratio near 1 | Native rate per track | Matching output to source achieves the same ratio *and* costs less disk and CPU *and* permits bit-perfect. |
| libsamplerate SINC_BEST 145 dB / MEDIUM 121 dB | All three sinc converters are **97 dB**, differing only in bandwidth | Checked the shipped docs. 97 dB is ~16 bits, capping the system at 16-bit whenever pitch is off centre. Switched to libsoxr. |
| Add an RP2040 to decode the jog encoder | Not needed | Sized for 600 PPR (~12,000 IRQ/s). At the agreed resolution it is ~800, which the Pi absorbs. |
| Keep the library on the SD card, not USB | USB is fine — and later, the only place it lives | That assumed a USB DDC sharing the bus with audio. The DDC is I2S; only Ethernet is left there, idle during playback. |
| Mitigate OLED noise (series resistors, minimal refresh) | Not needed for noise | The isolator puts the display on the near side of the gap. Refresh discipline still earns its place for burn-in and bus time. |
| Power quality is low priority | It matters | That rested on an async USB DDC owning the clock. With an I2S HAT inches from the Pi sharing power and clock, it does not hold. |
| `rotary-encoder,pin_a=5,pin_b=6` | Any other pins | GPIO 5/6 are oscillator-select lines — Pi pins *routed through* the isolator, so removing it does not free them, which the first phrasing invited. |
| Raw PCM removes the 4 GB container limit | Only where import expands the data | The source WAV/AIFF is capped by the same 32-bit chunk size, so playable length does not grow. The limit binds only when normalisation inflates a legal source past it. |
| USB gadget mode to reach the Pi over one cable | Impossible on a 3B+ | Its micro-USB port is power only. OTG exists on Zero-class boards and the Pi 4. |
| Library resident on the Pi's USB SSD | The removable stick **is** the library | DJ practice, not streamer practice: the stick is prepared elsewhere and swapped often, and a CDJ has no internal storage. The original framing was a music streamer that played DJ-style. |
| "SSH is the only way in" means content arrives over the network | Admin access only | Operation is fully network-independent; the cable can be unplugged during a set, which removes an interrupt source. |
| Normalise to raw PCM at import, off the Pi | No import step; sources play as they are | WAV/AIFF-only means there is nothing expensive to move — no decoder runs either way, and the byte swap and unpack are a few instructions per sample in a thread with no deadline. Sized for decoders this project had already excluded. |
| libsndfile must not appear in the playback path | It runs in the window thread | The ban's reason — it buffers, allocates and locks — only binds a thread with a deadline. In the window thread it brings big-endian AIFF, `sowt`, 24-bit unpacking and **RF64/Wave64** for free. |
| mmap the PCM file and mlock a window | libsndfile reads into a locked RAM ring in the output's own layout | With conversion in the path a RAM buffer is needed anyway, so mmap's advantage is gone. Dropping it also removes SIGBUS on a stick pulled mid-playback and the 32-bit address-space ceiling. |
| Metadata in SQLite or a sidecar | The folder tree is the index | With no import step, nothing writes a database. Lazy header reads for the highlighted row are also what catches every unplayable file before PLAY. |
| Restrict the rate budget to 44.1 and 48 kHz | All six family rates | Proposed and withdrawn the same day: sizing the window in bytes already fixes RAM regardless of rate, and v1 has no resampler. |
| **The material is long-form** — ambient and drone | The material is **various** | The sixth invented premise and the widest-reaching — load-bearing in ten places across four files, and found by `grep` rather than by argument. It began as a true statement about *part* of the material and hardened into a claim about all of it, which is harder to catch than an invention because the origin is a real quotation. It made the browsable-rows objection **worse**: folders of many short tracks are scrolled more than folders of twenty long ones. |
| **Dance material means beatmatching**, so pitch must be club-width | One deck, changing speed **like a record**. **±10% is enough** | The seventh, and mine — written *while* recording the sixth. The user said dance material exists; everything after "therefore" was inference, and had become the foundation of an open question within one message. With no second deck there is no drift to correct continuously, so losing pitch costs the **speed control** for that track — real, but not a sync failure. |
| `SOXR_VR` allocates in the audio callback, unboundedly | It allocates **nothing** — the probe had misconfigured `soxr_create` | Retracted in full. Every measurement created the resampler at ratio 1 and then set ratios from 0.90 to 1.10; the create-time ratio is what sizes the buffers. Declaring the span gives **0 events, 0 reallocs, 0 bytes** over 1,161 s with identical output. **Every figure was internally consistent and arithmetically correct, which is why verifying them could not catch it** — they were right about the wrong thing. Two things survive: `assert_no_alloc` cannot see libsoxr at all, and **declaring the pitch range at `soxr_create` is now a requirement** in `implementation.md`. |
| The 3B+'s 1.4 GHz gives v2 more headroom than the 3B's 1.2 | Size against 1.2 GHz anyway | The soft limit drops the clock at 60 C by default, raisable only to 70 and "might cause instability". A deck runs a continuous load in a box, so 1.2 GHz is the steady state. The 3B+ buys thermal mass and Gigabit Ethernet, not resampler headroom. Corollary: benchmark soaked, not cold. |

### Operating systems considered and dropped

Recorded because "surely something leaner" gets re-derived.

**DietPi** is the near miss — same base, leaner — and loses because it inserts its
own configuration layer owning `config.txt`, a second actor mutating a load-bearing
file. Worth reconsidering at the stripped-image stage. **Ubuntu Server** has its
own firmware and overlay packaging where both vendors' instructions target
Raspberry Pi OS. **Alpine** has no systemd, which breaks the mount design outright.
**Arch ARM, Fedora, openSUSE** are mainline-kernel or thin on Pi 3. **moOde,
Volumio, piCorePlayer** are excluded *because* they already drive HiFiBerry and
claim bit-perfect — they **are** the player, so basing on one means fighting MPD for
exclusive `hw:` access. **Buildroot, Yocto, NixOS** are a possible destination for a
stripped image but only after the measurements: bring-up needs `alsacap`, `amixer`,
`dtoverlay -h`, `vcgencmd`, `rfkill`, `blkid` and `findmnt`, and a minimal image
strips all of them.

Three things the OS choice does **not** settle: whether the rootfs ends up
read-only, whether bring-up and production get separate images, and how the deck
starts at boot ([#8](https://github.com/tamatebox/deck-pi/issues/8)).
