# Decisions

Design settled 2026-09-09. The reasoning, which does not expire when a module
lands. `README.md` carries what is built.

**Each row is a ruling.** Reasoning is here only where someone would otherwise
re-derive the opposite; elsewhere the ruling is its own argument. Findings that
constrain code live in that code's doc comments instead, which is nearer the reader
who needs them — `src/media.rs` for the volume UUID and the mount test,
`src/cue.rs` for path escaping, `src/input.rs` for the clock, `src/file.rs` for the
shift.

## Settled

| Decision | Why |
|---|---|
| Raspberry Pi 4 Model B | The 3B+ this started on died on 2026-09-21 and a Pi 4 was already in the house. Same 40-pin header and footprint, so nothing in the board stack depends on which it is — and nothing in the code did either, which the move proved rather than assumed. See the reversal below for what the change cost and what it did not. |
| One Pi per deck | Per-track rate switching is then free — reopening this deck's DDC cannot interrupt a different machine. |
| Digi2 Pro + IsolatorPi III | Dual oscillators in master mode take the Pi's PLL out of the clock path; the isolator keeps Pi ground noise off the audio boards and gives the controls a non-isolated header. **Half of this has since gone**: the controls are on a Pico, so the header the isolator offered has no use, and the isolator itself is optional as of 2026-09-16 — see the row below. The oscillator half is the part that decided the board and it is unaffected, being the Digi2 Pro's own. |
| Separate clean supply on J1 | The isolation is only real if the audio side is powered independently. 5 V, not J1's 3.3 V floor: the rail passes through to a 5 V HAT. |
| Fit the isolator last, not first — **and it is now optional** | The manual (§J-1) says prove audio *before* inserting it. A direct-mounted Digi2 Pro runs the whole v1 software stack — but is not an audio-quality baseline. **Settled 2026-09-16 by a usage answer**: the isolator is an improvement the deck does not require, so the built configuration is Pi plus Digi2 Pro and bring-up stage C is something that may never happen. The research stays in `hardware.md` under headings that say they are conditional, because it was read out of the manual and off a photograph and would otherwise have to be done twice. **One consequence reaches the built deck anyway**: the ID EEPROM lines do not cross J6, so the `config.txt` overlay line is redundant while no isolator is fitted and load-bearing the moment one is. |
| WAV / AIFF sources only | Uncompressed, so no decoder ever runs on the Pi. RF64 and Wave64 come free with libsndfile and lift the 2 GiB container ceiling. |
| Native rate and depth per track | Upsampling costs disk and CPU and buys nothing. Matching rates is also what makes bit-perfect possible. |
| Locked int32 ring around the playhead | Decouples track length **and** sample rate from RAM — cost is constant in both. Was mmap + mlock; see Reversed. |
| The window's two halves are relative to the **direction of travel** | Not to increasing frame number: an append-only ring accumulates for free only on the side the playhead has passed. A forward-only refill served a descending playhead **0 of 12 periods**, measured. Direction comes from successive playhead values, so nothing new is plumbed, and an explicit seek clears it. Costs one missed period per relocation — reverse playback is served, not gapless. |
| Wireless off, Ethernet only | Fewer interrupts, and the radio is dual-band on both the 3B+ and the Pi 4, so this removes a 5 GHz transmitter too. Confirm wired access *before* disabling. On the Pi 4 it also takes a little heat out of a box that has no fan in it. |
| Buttons and encoders on GPIO, kernel-decoded | No MIDI jitter, no USB polling interval. Never userspace polling. |
| No LEDs | Keeps the wiring simple. Not a noise decision — a statically driven LED is DC and quieter than the display. The display shows state instead, and can show *why*. |
| Everything in Rust, one process | v1 would be comfortable in Python but v2 would not. The split then collapsed anyway: the browser needs libsndfile too, so a language boundary would mean binding it twice. `embedded-graphics` also gives the device-swap reversibility that kept the UI in Python. |
| The realtime setup is applied **and read back**, in `src/rt.rs` | `mlockall`, `SCHED_FIFO` and core pinning are properties of the process, not the code, so no test reaches them — and all three fail silently with audio still coming out. Each is verified against the kernel's own view, and two are answered up front from `getrlimit` so a failure prints the missing `limits.conf` line. The pre-fault measures its own reach, the first version having touched one page. |
| **Fence when a fence costs no test surface; nudge — in words — when it would** | Recorded because one day produced both dispositions and either alone generalises wrongly. `CueStore::set` stayed public with a note that says it is load-bearing, because narrowing it would cost the store its own tests; `no_alloc` moved into the crate because that fence was free. The question is what the fence costs, not which is safer in the abstract. |
| Enforce the callback rules with `assert_no_alloc` | A global allocator wrapper that fails loudly is what turns the discipline from intent into something checked. **Scope correction, measured:** it wraps Rust's `GlobalAlloc`, so a C library calling glibc is invisible to it — which is nothing for libsndfile in the window thread and everything for libsoxr in v2's callback. |
| Read files through a hand-written libsndfile FFI | About forty lines of `extern "C"`. The binding crates stopped moving in 2021; at this size owning the declarations is sturdier and auditable. `symphonia` cannot be used — no RF64 or Wave64. |
| Output format is `S24_LE`, and the ring matches it | Read from kernel source rather than waiting for hardware: `WM8804_FORMATS` offers no `S32_LE`, so the intersection with `bcm2835-i2s` is `S16_LE / S24_LE`. Right-aligned in a 32-bit word, so the ring holds `sf_readf_int`'s value shifted right 8, done off the deadline. Still a pure shift. |
| GPIO 5 is the 44.1 kHz crystal, GPIO 6 the 48 kHz one | Reassigning them does not merely break oscillator select: the driver falls back to a 27 MHz sysclk, which is the WM8804's **PLL** reference, so audio keeps playing through the high-jitter path the build exists to avoid. |
| `sf_readf_int` supplies the ring | Its convention puts the source MSB at the destination MSB, so the byte swap and the 24-bit unpack are not our code at all. The only thing added is the right-8 shift. |
| Format scope is exactly the DDC's limit | 44.1 / 88.2 / 176.4 and 48 / 96 / 192 kHz, int16 and int24 only. Nothing separate to remember: if the Digi2 Pro can send it, the deck plays it. |
| Every supported conversion is a pure shift | Nothing is rounded, scaled or truncated anywhere. Excluding 32-bit is what buys this — float32 needs a clipping or scaling decision, and scaling would be a gain stage. |
| The window is sized in **bytes**, not seconds | `min(60 s, N MiB)` keeps RAM constant across all six rates. N is **not only a jog-feel parameter**: the forward half is also how long playback survives a knocked connector. At 64 MiB that is 60 s at 48/24 but 21 s at 192/24 — see [#9](https://github.com/tamatebox/deck-pi/issues/9). |
| **exFAT and HFS+, both from v1** | The criterion is native read-write on macOS *and* a mature in-tree Linux driver. Supporting both costs nothing, mounting being a udev concern at a fixed path. FAT32 is out on the 4 GiB file limit, which bites a 192/24 track at 31 minutes; ext4 because the preparing machine cannot write it cleanly. |
| Journaled HFS+ mounting read-only is a feature here | The driver forces `SB_RDONLY` and offers `force` at your own risk. That is already the policy for removable media, so the restriction and the requirement are the same thing. Never pass `force`. |
| Do **not** pass `nodecompose` on an HFS+ mount | The driver composes filenames on the way out by default, so Japanese names arrive precomposed and no normalisation pass is needed. Pass it and every dakuten becomes a second code point. |
| APFS is the one still requiring out-of-tree code | Not in `fs/`, so it would mean FUSE or a module rebuilt per kernel update, both reverse-engineered, neither able to read FileVault. Moot: the drive is HFS+. If it ever matters, the fixed-path design means a driver plus one udev branch and zero lines of Rust. |
| Treat the mount as fallible, but do not design around it | Removal is the dominant case. The two other paths — USB re-enumeration after a power dip, and a bumped connector in a venue — do not change the code: `read_dir` returns a `Result`, so the requirement amounts to "do not `unwrap()`". The audio side already survives it. |
| What the DAC accepts is out of scope | S/PDIF is unidirectional, so a DAC that cannot lock goes silent and the software can never detect it. A configurable ceiling was proposed twice and dropped twice: the deck cannot tell which DAC is attached, so it would be a claim, and a stale claim sounds certain while being wrong. |
| The UI distinguishes "no stick" from "stick I cannot read" | Showing only `No USB` makes a formatting mismatch look like broken hardware. Say *why*, not just *that*. |
| A udev rule calls `systemd-mount`, at a **fixed path** | Nothing mounts removable media on a headless box. `systemd-mount` creates a transient unit, so teardown on removal is automatic where a direct `mount` would leave it unowned. It also keeps mount privilege out of the audio process, which needs no root at all. |
| Match on `ID_FS_TYPE`, not "the first block device" | A Mac drive with a GUID partition map carries a vfat EFI partition, so taking `sda1` would mount that instead of the music. Matching the two filesystems does partition selection as a side effect — and is needed anyway, since they take different option names. |
| The fixed mount point is what enforces "one stick" | A second volume finds the path occupied and does not mount, so "the first one only" falls out of path uniqueness instead of needing selection logic. |
| `--automount=no`, explicitly | Automount is implied for removable devices and makes the mount point exist whether or not media is present, destroying the simplest presence test. **But "one `stat`" was too strong, and this row used to say it** — see below. |
| Presence is `st_dev` against the parent's, **not existence** | Correcting the row above, found while building `src/media.rs`. An existence test additionally assumes systemd *removes* the directory on unmount, and a failed unit, a crash or a stray `mkdir` leaves it behind — reporting a stick that is not there, a third way to confuse the two states this design exists to tell apart. Measured; the numbers are in `src/media.rs`. |
| Ownership comes from mount options on both filesystems | exFAT has no POSIX ownership; HFS+ carries the preparing Mac's uids. Either way `uid=`/`gid=` decide who can read, and getting them wrong means the mount succeeds while the application reads nothing. Numeric only — the kernel resolves no names. Exact option lists are in `implementation.md`, read from the drivers. |
| The medium is solid-state — never a spinning disk | Recorded so spin-up current, first-access latency and scattered seeks are not re-derived as concerns. The worst case the window thread asks for is 1.5 MB/s, at 192/24, so sustained read is a non-question either way. |
| The cue key's volume UUID comes from `blkid`, not from the mount | Neither filesystem exposes its serial through a file API, and the two formats differ, so store it as an opaque string rather than parsing it. **Corrected: this row used to describe HFS+'s shape wrongly** — the raw volume id never appears, `libblkid` hashing it first. The error was harmless because the value is only ever stored and compared, which is also why two tests asserting contradictory shapes both passed. Implemented with no subprocess; the mechanism is in `src/media.rs`. |
| **No volume UUID is a browsable state, not a failure** | The stick browses and plays; what it loses is the cue store's key. Encoded in the type (`Browsable { uuid: Option<String> }`) rather than left to a caller to remember, because a silently non-persisting cue button is worse than one that explains itself. |
| **Two byte-identical sticks sharing their cues is correct, not a collision** | Raised by review and recorded as *not* a defect, so it is not re-found and filed as work. A clone should behave like the stick it copies, and the fixed mount point means only one can be mounted at a time. |
| One stick, the first one, mounted read-only | A stick pulled mid-set cannot corrupt the filesystem, and there are no dirty pages to write back. |
| Dotfiles are hidden, and on this medium that is **not cosmetic** | Found while building the browser. A Mac-prepared stick carries `._name` AppleDouble twins, and `._piece.wav` would sit directly beside `piece.wav` reading as a broken duplicate of it. Note this is the *only* filter: an unplayable file is still shown, marked, with the reason, because hiding refusals would make a folder of FLAC look empty. |
| Folders first, then files; each group in **natural** order | `readdir` order is neither stable nor meaningful, so some order had to be imposed. Folders first matters more than usual here: with two browsable rows on the smallest candidate panel, collecting the navigable rows at the top is the difference between seeing a folder and scrolling to find it. Numeric-aware, which costs nothing on unnumbered names, so no assumption about the material is involved. The tie-break on raw bytes makes the order **total**, without which a reload could reshuffle rows under the selection. |
| The selection does not wrap at either end | A detented encoder gives no feedback that a list ended, and on a two-row panel wrapping is indistinguishable from a mis-scroll. A CDJ's list does wrap, so this is a deliberate departure and the reason is the row count. |
| Header reads are driven by renders, not by encoder events | Redraws are already coalesced to 30-50 ms, so only rendered positions need headers and a fast spin's intermediate ones are skipped. The redraw budget bounds the read load and no second timer is needed. |
| Cache header reads by path, and read the whole visible page | The cache is what makes it cheap rather than the debounce: scrolling one row leaves every other visible row already read. **The figures were first sized against sixteen rows, which is no candidate in [#2](https://github.com/tamatebox/deck-pi/issues/2)** — those give four to thirteen. The conclusion survived the correction; the arithmetic did not, and a wrong number supporting a right conclusion is what gets re-derived later. |
| **Three input disciplines, not one** | BACK, PLAY/PAUSE and ENTER fire on key-down, where latency is felt. CUE emits press *and* release because the Cue Point Sampler continues while held and so cannot wait for a threshold. Only FF and REW get tap-versus-hold, because only they carry two meanings. **A uniform rule would be simpler and wrong: PLAY held slightly long would emit a hold and never a tap, so the deck would not start.** **Superseded 2026-09-18 — there are two** ­— see *Reversed*. The uniform-rule argument survives its own discipline and is why PLAY is still `Simple`. |
| The hold threshold is timed from a **monotonic read**, not the event's timestamp | Using the event's is the obvious thing and it is wrong: kernel input timestamps are `CLOCK_REALTIME` by default, so an NTP step — plausible with the maintenance cable in — turns a tap into a forty-minute hold. Taking the time as an argument is also what makes tap-versus-hold testable with no device and no sleeping. **Superseded 2026-09-18: the decoder reads no clock at all.** The trap was real and the defence was right; both are moot, which is exactly the shape that gets re-derived from an empty page — see *Reversed*. |
| The encoder's axis type is **not** assumed | The overlay reports relative or absolute depending on a parameter, so both are handled and the code does not depend on a line of `config.txt` nobody has run yet. The absolute flavour needs one extra rule: the first reading sets a baseline and emits nothing, or an encoder starting anywhere but zero scrolls that far on its first event. |
| Cue points live on the Pi, not the stick | Keyed by volume UUID plus relative path. The stick is content; the Pi owns state it created. Consequence: cues would not travel between two decks. |
| The cue file is hand-written, line-based, and **escapes the path** | The whole need is a map from a path to a `u64`, smaller than the crate that would read it, and a format you can `cat` is worth having on an appliance you SSH into. **What decides the format is that a filename can contain a newline** — verified as a real HFS+ filename — so a naive `frame<TAB>path` line is not untidy but wrong. |
| The cue key is **raw bytes**, not a `String` | A lossy conversion maps every invalid sequence to the same replacement character, so two different broken names would collide on one cue — silently, and only on the medium that produced them. |
| Setting a cue **writes through, atomically** | A deck gets switched off at the wall, so flushing on shutdown would routinely lose the last thing set. Atomic because a power cut mid-write would otherwise lose *every* cue for that stick rather than one. Sorted, so re-saving is byte-identical and a diff shows what changed. |
| State lives in `$XDG_STATE_HOME/deck-pi`, one file per volume | State, not config or cache: the deck created it and cannot regenerate it. One file per volume means dropping a stick you no longer use is deleting one file. A volume name that cannot be a filename is **refused, not sanitised** — mangling two names into one file would merge their cues. |
| **CUE is one button with three behaviours, and there is no separate STOP** | Paused, CUE **sets**; playing, it **returns** and pauses; held at the point, it **plays while held**. Nothing but the deck's own state selects between them, which is what keeps it one button rather than a button and a modifier, and each is the only sensible reading of the state it fires in. The finding that matters: **this deck needs no STOP**, because returning to the cue point and standing by *is* stopping — so the hold gesture is free for preview instead of being spent on a stop the transport already has. Costs no new mechanism. **This was once credited to an outside player's manual.** The credit is gone and not one behaviour moved with it, which is what says the credit was never the thing making them right. |
| **Loading a track waits at frame zero, not at its stored cue** | Settled by the user, and surveyed rather than assumed. Both behaviours are real wherever stored cues exist and **jumping is the opt-in one**, so frame zero is the answer that needs no explaining: it is where the file starts, and a load that lands somewhere the operator did not choose is the surprising one. **The cost is named rather than hidden:** with the playhead at zero and a cue elsewhere, the first CUE press overwrites the stored point — specified behaviour, on a position the operator did not choose, and the most likely first gesture after a load. Not to be fixed by special-casing: a mode that exists only just after a load is invisible in the code and unlearnable at the panel. |
| Auto cue is not adopted | The mechanism skips the silent lead-in on load and places the cue where sound starts, on a threshold. **The rejection stands but not its original framing**, which split club from quiet material — the deck plays both. It stands on the quiet case alone: one piece that opens below the threshold deliberately is enough to make an automatic decision wrong, and a rule has to be right for everything on the stick. |
| **An FF/REW tap loads the next track and waits at its head** | Settled by the user. **The first version of this row justified it by attributing it to an outside player, and the attribution was both false and unnecessary** — that machine plays on through a track change, and the rule was right anyway. Shares one rule with the row below rather than being two that could drift: **nothing starts making sound that PLAY did not start.** One consequence the software leans on — a track change therefore always contains a pause, which is what lets the threads and sink be per-track and every drop happen off the deadline. **Superseded 2026-09-18 as to *which button*, and only that** — see *Reversed*. The behaviour is unchanged and so is the rule it shares. |
| **A deck with nothing loaded refuses every control, and the transport enforces it** | Not the dispatch, because two copies of a state machine's rule is how two orders drift. **This is a consequence of `Stopped` becoming reachable**: while it was constructed and never stored, nothing that read the state could be wrong, so the guard was not merely absent but unnecessary. Found by a hang rather than a failure — `AtEnd::Stop` means a caller that plays without loading loops on `Paused` for ever. |
| **The threads and the sink live as long as the track is *loaded*, not as long as it is *playing*** | The natural reading is the other one and the first version took it. Then PAUSE would tear down an ALSA device and a 64 MiB ring mid-set, and a deck on the last frame could not be cued back into. What ends a run is unloading, the medium going, or a fault. Affordable **only because a track change always contains a pause**. |
| A track that reaches its end stops | Nothing starts on its own. In a venue, a next track beginning while attention is elsewhere is worse than a silence, and PLAY is right there. Auto-advance is a small addition later if wanted. |
| Raspberry Pi OS Lite (64-bit) is the base | Four constraints already pin it: the HiFiBerry overlay and machine driver live in the **downstream** tree; the mount design commits to `systemd-mount`; `config.txt` on the FAT partition is what makes a bad setting recoverable by reading the card on a Mac; and exfat and hfsplus must be in-tree. 64-bit is just the current default. |
| **The v2 ADC is on I2C, which is what chose the display** | One unresolved part decided the fader's ADC, the panel, and the button count. Settled by a **usage answer, not arithmetic**: the I2C branch offers twelve buttons with a small panel *or* eight with an SPI panel, and twelve is only worth having if four more controls are wanted — they are not. So the branch that spends those pins on the panel wins with nothing given up, and the part is better on merit anyway. **Superseded, 2026-09-15, and by more than arithmetic** — see *Reversed*. This row's whole argument is a trade between *twelve buttons with a small panel* and *eight with an SPI panel*. **Both sides of that trade have left the Pi**: the buttons to the Pico, then the panel after them. The ADC choice may well still be right, but it is right for none of the reasons recorded here, which is a different thing from the numbers having moved. What survives is the ADC half, and even that is newly open, because the Pico carries an ADC of its own and nobody has decided whether the fader uses it. **Two corrections came out of settling it.** An earlier table paired the I2C ADC with the larger panel *and* twelve buttons, spending the same four pins twice — **freeing SPI0 is not leaving it empty.** And the tally then balances at **zero spare**, which promotes two properties of an unbought panel to load-bearing; [#2](https://github.com/tamatebox/deck-pi/issues/2) holds them. |
| **A part you own is a fact; a part you might buy is a constraint** | Written down because the line was being crossed — and then **this row's own example crossed it.** `WM8804` and `CA-IS376x` were offered here as the illustration of the first half, as parts "on the bench". They never were: when that sentence was written the Pi 3B+ was the only owned part, and the claim cost two sessions a wrong inference before it was caught. **Do not restate the inventory here, or anywhere it will not be maintained** — a list of what is owned goes stale, which is the whole failure this row exists to name, and no document in this tree carries one today. The two chips belong to the *second* half — chosen, unbought — and naming them did the thing this row warns of: `src/file.rs` scopes `SUPPORTED_RATES` to "exactly what the Digi2 Pro can send", so an unbought board is a design premise in code. Left standing, because the format scope comes from the sink's capability or from nowhere; recorded so it is a known debt rather than an unnoticed one. An unbought component otherwise gets its *requirement* recorded instead — a catalogue number there turns a purchase into a design premise. **A requirement is also what survives a donor part arriving**: it becomes a check to run against a real object rather than an argument to win on paper. The same reframing made a temperature finding stronger: not "this series is rated to +50 °C", but **an enclosure hot enough to throttle the Pi is already outside a commodity panel component's rating**, which survives any substitution — [#6](https://github.com/tamatebox/deck-pi/issues/6). **That reframing has since been paid off twice over.** The sentence was written with the 3B+'s 60 °C in it, and the board became a Pi 4 that throttles at 80: had the number stayed in, the argument would have looked weakened by the move when in fact it is strengthened, because 80 °C inside a box is further outside a commodity part's rating than 60 was. The panel also left the Pi entirely for the Pico — and the claim still holds, because it was never about the panel. |
| FF / REW are a silent seek in v1 | An audible scan needs the resampler, which would give v1 a second mode and break "unconditionally bit-perfect". In v2 it becomes `r = 4` on the existing rate variable — no new mechanism. |

| **The panel is not where the chain is confirmed** | Decided 2026-09-16, and it overturns a sentence `README.md` carried from the start: "the rate and depth actually in use, which is how you confirm the chain is doing what it claims". It does not confirm anything. The panel prints what the deck believes, so **a deck wrong about its own output prints the wrong number with the same confidence** — a check that shares a failure mode with the thing it checks is not a check. The confirmation is `--device=`, which reads `hw_params` back out of `/proc/asound` and asks whether the mixer is empty, and which found nothing wrong across all six rates on 2026-09-15. The fields stay on the panel because they are free on every candidate geometry, not because they earn their place. |
| **No bit-perfect indicator, in v1 or v2** | The obvious v2 replacement — a binary "is the resampler in the path" — was proposed and dropped the same day. **It is determined by the controls**, so it tells a hand what that hand is already doing, and the fader's centre detent is what `decisions.md` already calls the thing that makes UNITY's "near centre" a physical fact rather than an inference. The one form that would carry information is the deck *disagreeing* with the controls: [#3](https://github.com/tamatebox/deck-pi/issues/3)'s fallback to unity for a rate the resampler cannot sustain, which the deck chooses and the hand cannot see. **Measured 2026-09-16 and it looks unreachable** — 4.25x realtime at 192 kHz soaked at 1.2 GHz, worst block half a period — so the indicator would announce an event that does not happen. Revisit only if that measurement stops holding. **Re-measured 2026-09-22 on the Pi 4 that replaced that board: 14.50x and 16% of a period.** The fallback recedes rather than approaching, so this row gets further from needing a revisit, not nearer. |

## Reversed during design

Recorded because the superseded reasoning is plausible enough to be re-derived by
accident. This section is the one thing in this file with no other home.

| Was | Now | Why it flipped |
|---|---|---|
| **An FF/REW tap loads the next track**, hold seeks | **TRACK SEARCH is its own pair of buttons; SEARCH only seeks** | Decided 2026-09-18, and **the behaviour did not change — its button did.** `controls.md` compressed four transport buttons into two because two dedicated buttons cost two pins on a header `hardware.md` had closed at zero spare. **That price no longer exists**: the controls are on a Pico, and the CDJ-200's `KSWB` panel reports *six* buttons on one analog line, so the pair split at no cost in pins at all. What the original argument really rested on — that it must not become a hidden *mode* on the browse encoder — is untouched. Three things came with it and none is cosmetic. **The seek now starts on the press, 400 ms earlier**, there being no second meaning to wait out. **Two disciplines remain where there were three**, and the whole tap-or-hold machinery went with the third — `Action::Tap`, `HoldStart`, `HoldEnd`, `HOLD_AFTER` and `Decoder::tick`, which would otherwise have been declared and never constructed, the first shape in `implementation.md`'s table. And **four tests inverted rather than being deleted**: `a_hold_that_had_not_fired_yet_is_dropped_rather_than_turned_into_a_tap` asserted that a press younger than the threshold must *not* produce an action, because it was going to be a tap and inventing one would change track; the same press is now a running seek, and dropping it silently is what leaves the transport in `SeekingForward` for ever. The assertion is the exact opposite and the reasoning behind both is worth keeping. |
| The hold threshold is timed from a monotonic read | **Nothing in the input path is timed** | Same change, recorded separately because the *reason* has no other home. The superseded row explains why the event's own `CLOCK_REALTIME` timestamp was refused — an NTP step during maintenance turning a tap into a forty-minute hold. **There is no tap, so there is no trap**, and the decoder takes no time argument at all. The danger is dormant, not solved: anything that later measures a gesture's duration from an input event walks straight back into it. |
| **A Pioneer CDJ-350's operating instructions are the reference for what a button means** | **There is no reference player; every control stands on its own reasoning** | Decided 2026-09-21 by the user: the manual had become an authority rather than a reference, and questions about this deck were being settled by looking up what another machine does. **Not one behaviour changed when it went, and that is the finding.** CUE's three behaviours, the absence of a STOP, the refusal of auto cue and TRACK SEARCH waiting at the head all survive with their reasoning intact, because each rests either on the deck's own rule — *nothing produces sound that the operator did not press PLAY for* — or on being the only sensible reading of its own state. **A citation that can be removed without moving a single behaviour was never what made the behaviours right.** What does change is the framing: `controls.md` was organised around *departures* from that player, and with no reference there is nothing to depart from, so every rule there is now the deck's own decision or it is unjustified. **Recorded rather than left silent for two reasons.** "Surely we should check what a CDJ does" is exactly the shape of thing this section exists to stop being re-derived. And the reference was genuinely *read* rather than recalled, so a reader working back through the history will find careful, correctly-cited sentences and wonder why they went — they went because being correctly cited is not the same as being relevant to this deck. The scar worth keeping is the one in the row above: an earlier `controls.md` justified the head-of-track pause by attributing it to that player, the attribution was false, and the rule was right regardless. |
| Unify the library at 96 kHz to keep the resample ratio near 1 | Native rate per track | Matching output to source achieves the same ratio *and* costs less disk and CPU *and* permits bit-perfect. |
| libsamplerate SINC_BEST 145 dB / MEDIUM 121 dB | All three sinc converters are **97 dB**, differing only in bandwidth | Checked the shipped docs. 97 dB is ~16 bits, capping the system at 16-bit whenever pitch is off centre. Switched to libsoxr. |
| Add an RP2040 to decode the jog encoder | Not needed | Sized for 600 PPR (~12,000 IRQ/s). At the agreed resolution it is ~800, which the Pi absorbs. **Still true, and it is not what the row below overturns** — that one is about v1's buttons and browse encoder, and turns on pins and wiring rather than on interrupt load. The jog wheel is untouched by it. **But the conclusion has been overtaken even though the reasoning has not:** "do not add an MCU" was advice against a cost, and the MCU is now there for other reasons. Whether the jog goes on it is open, and is a usage answer rather than an arithmetic one. |
| Controls wired straight to the Pi's header, one `gpio-key` overlay each | **A Pico 2 H carries the buttons and the browse encoder, and reaches the Pi as a USB device** | Decided 2026-09-15, by a usage answer rather than by argument: the board and the switches are in hand. What makes it nearly free is that `src/input.rs` was already written to know nothing about wiring — it matches standard keycodes and takes detents as `EV_REL`/`REL_X`, so a composite HID device lands on the paths it already reads. **What is unchanged is the decoding, and only that** — an earlier draft of this row said "the deck's code does not change", which is the flattering version and false. `Devices` has no re-open path: `read_pending` drops a device that goes away and counts it `lost`, and `wait` on an empty list sleeps the timeout and returns `Ok(false)`. Against `gpio-key` that was right, because an overlay's node exists from boot and a vanishing one really is a fault. A USB device vanishing is ordinary — replug, bus reset, a knocked cable — so this change installs a deck that plays on with every control silently dead. Rediscovery, and a deck that can say it has no controls, are **new work this reversal creates**, not something it gets free. `Devices::open` erroring on a missing path changes meaning too: absent at start is now an enumeration race, not a missing button. One thing improves: the autorepeat guard at `src/input.rs` was written as defensive — `gpio-key` does not repeat — and a USB HID keyboard does, so it becomes load-bearing and its test becomes a real-hardware property. What moves is **debounce and quadrature decoding, from the kernel into the Pico's firmware** — reversing `implementation.md`'s "decode encoders and debounce buttons in the kernel", whose real target was userspace polling, which this is not. What goes away: seven overlay instances, the seven device nodes behind them — and the defect that came with them, `Device::wait` polling one of the seven — the control GPIO assignments, and stage C's rewiring onto J4. What arrives: a second processor with its own firmware — **Rust, decided with the rest**, which is what keeps `CLAUDE.md`'s no-Python invariant intact on a board whose usual language is MicroPython — and one more device on the USB bus the stick is on. Unplanned confirmation on the day: a Pico in BOOTSEL is a **vfat** block device on that bus, and the mount rule ignored it while the music stick stayed mounted, which is the `ID_FS_TYPE` matching earning its keep against a second case the row that chose it never named. **A second unplanned confirmation, 2026-09-21, and it is a property rather than a piece of luck: the boundary is a standard HID device, so either side can be replaced without the other knowing.** Neither end names the other — the Pico emits standard keycodes and `EV_REL`/`REL_X`, `src/input.rs` matches those and nothing else — so the deck would take a USB keyboard in place of the CDJ panel, and the panel would take any Linux host in place of the Pi. The Pi's PMIC failed that day, 3V3 shorted to ground and the board unrecoverable, and the Pico, the fader, the switch panel, the test-clip wiring and every measurement taken through them were untouched; the probe was read from a Mac the same afternoon with no Pi in the room. On the header, each of those connections would have to be remade on a replacement board and none of it could be checked until one arrived. **Where the separation stops is worth seeing too:** audio still leaves through the header, so replacing the Pi is a question about the Digi2 Pro and never about the controls. **None of this was a reason for the move** — the argument was pins and wiring, and a benefit found afterwards does not improve an argument. What it changes is the cost of going back. |
| The panel sits on the Pi's SPI0 | **The panel sits on the Pico too, and the Pi ships it pixels** | Decided 2026-09-15, immediately after the row above and for the same reason — once the Pico is there, the header is the expensive place to be. **The split is deliberate: the deck still draws.** Fonts and layout stay in the deck, which keeps `CLAUDE.md`'s "one process — engine, browser and display" true, keeps the rendering testable on a Mac, and keeps the 12x12 / 16x16 Japanese faces that `tools/panel-compare` exists to judge out of firmware. The `DrawTarget` impl that was always the plan targets a USB packer instead of an SPI driver. Consequence worth having: **the panel choice leaves the Pi's pin budget entirely**, which is the premise [#2](https://github.com/tamatebox/deck-pi/issues/2) is stuck on. Consequence, and the premise in this sentence was wrong until 2026-09-16: it said frame traffic "shares the 3B+'s single USB 2.0 with the window thread's reads". **It does not, to any degree worth planning around.** The RP2350 carries a USB 1.1 controller, and the deck's Pico enumerates at 12 Mbit/s beside a stick and an Ethernet adapter at 480 — so the ceiling is the Pico's link, about 40x below the bus the stick uses. What survives is the *other* half: a 320x240 16bpp full frame is 153,600 bytes, which at a full-speed device's reachable bulk rate (**estimated** ~1 MB/s) is ~150 ms against a 40 ms cadence. That is now a bound read off a datasheet rather than a thing to measure, and its answer is not partial updates but **not sending 16bpp at all** — see `architecture.md`. |
| Keep the library on the SD card, not USB | USB is fine — and later, the only place it lives | That assumed a USB DDC sharing the bus with audio. The DDC is I2S; only Ethernet was left there, idle during playback. **No longer only Ethernet** — the controls and the panel moved to a Pico on that same bus, so the stick's reads now share it with frame traffic. See *Reversed*. |
| Mitigate OLED noise (series resistors, minimal refresh) | Not needed for noise | This rested on the isolator putting the display on the near side of the gap — and **there is no gap now**, the isolator being optional and the panel being on the Pico, reached over USB rather than over anything the Pi's ground touches. Refresh discipline still earns its place for burn-in and bus time. **"Bus time" no longer means what it meant.** It meant SPI, contended with nothing. The panel is on the Pico now, so it means the Pi's single USB 2.0 — shared with Ethernet *and with the stick the window thread reads the audio from*. That is the first place this reversal reaches the **audio path** rather than the control surface, and the sentence reads as current when it is not. |
| Power quality is low priority | It matters | That rested on an async USB DDC owning the clock. With an I2S HAT inches from the Pi sharing power and clock, it does not hold. |
| `rotary-encoder,pin_a=5,pin_b=6` | Any other pins | GPIO 5/6 are oscillator-select lines — Pi pins *routed through* the isolator, so removing it does not free them, which the first phrasing invited. |
| Raw PCM removes the 4 GB container limit | Only where import expands the data | The source WAV/AIFF is capped by the same 32-bit chunk size, so playable length does not grow. The limit binds only when normalisation inflates a legal source past it. |
| USB gadget mode to reach the Pi over one cable | Impossible on a 3B+ | Its micro-USB port is power only. OTG exists on Zero-class boards and the Pi 4. **The board is now a Pi 4, so this row's objection has expired** — the reason it stays is that nobody has asked for gadget mode since, and a reopened question needs a reason of its own, not just the removal of an obstacle. |
| Library resident on the Pi's USB SSD | The removable stick **is** the library | DJ practice, not streamer practice: the stick is prepared elsewhere and swapped often, and a CDJ has no internal storage. The original framing was a music streamer that played DJ-style. |
| "SSH is the only way in" means content arrives over the network | Admin access only | Operation is fully network-independent; the cable can be unplugged during a set, which removes an interrupt source. |
| Normalise to raw PCM at import, off the Pi | No import step; sources play as they are | WAV/AIFF-only means there is nothing expensive to move — no decoder runs either way, and the byte swap and unpack are a few instructions per sample in a thread with no deadline. Sized for decoders this project had already excluded. |
| libsndfile must not appear in the playback path | It runs in the window thread | The ban's reason — it buffers, allocates and locks — only binds a thread with a deadline. In the window thread it brings big-endian AIFF, `sowt`, 24-bit unpacking and **RF64/Wave64** for free. |
| mmap the PCM file and mlock a window | libsndfile reads into a locked RAM ring in the output's own layout | With conversion in the path a RAM buffer is needed anyway, so mmap's advantage is gone. Dropping it also removes SIGBUS on a stick pulled mid-playback and the 32-bit address-space ceiling. |
| Metadata in SQLite or a sidecar | The folder tree is the index | With no import step, nothing writes a database. Lazy header reads for the highlighted row are also what catches every unplayable file before PLAY. |
| Restrict the rate budget to 44.1 and 48 kHz | All six family rates | Proposed and withdrawn the same day: sizing the window in bytes already fixes RAM regardless of rate, and v1 has no resampler. |
| **The material is long-form** — ambient and drone | The material is **various** | The sixth invented premise and the widest-reaching — load-bearing in ten places across four files, and found by `grep` rather than by argument. It began as a true statement about *part* of the material and hardened into a claim about all of it, which is harder to catch than an invention because the origin is a real quotation. It made the browsable-rows objection **worse**: folders of many short tracks are scrolled more than folders of twenty long ones. |
| **Dance material means beatmatching**, so pitch must be club-width | One deck, changing speed **like a record**. **±10% is enough** | The seventh, and mine — written *while* recording the sixth. The user said dance material exists; everything after "therefore" was inference, and had become the foundation of an open question within one message. With no second deck there is no drift to correct continuously, so losing pitch costs the **speed control** for that track — real, but not a sync failure. |
| `SOXR_VR` allocates in the audio callback, unboundedly | It allocates **nothing** — the probe had misconfigured `soxr_create` | Retracted in full. Every measurement created the resampler at ratio 1 and then set ratios from 0.90 to 1.10; the create-time ratio is what sizes the buffers. Declaring the span gives **0 events, 0 reallocs, 0 bytes** over 1,161 s with identical output. **Every figure was internally consistent and arithmetically correct, which is why verifying them could not catch it** — they were right about the wrong thing. Two things survive: `assert_no_alloc` cannot see libsoxr at all, and **declaring the pitch range at `soxr_create` is now a requirement** in `implementation.md`. |
| The 3B+'s 1.4 GHz gives v2 more headroom than the 3B's 1.2 | Size against 1.2 GHz anyway | The soft limit drops the clock at 60 C by default, raisable only to 70 and "might cause instability". A deck runs a continuous load in a box, so 1.2 GHz is the steady state. The 3B+ buys thermal mass and Gigabit Ethernet, not resampler headroom. Corollary: benchmark soaked, not cold. **Superseded by the row below** — the board is no longer a 3B+ and the mechanism this row turns on does not exist on the new one. The corollary outlives it. |
| Size against 1.2 GHz | **There is no planning clock; every clock this board reaches is enough** | The board became a Pi 4 on 2026-09-22, and the row above turned entirely on `temp_soft_limit`, which is documented as **3A+/3B+ only**. A Pi 4 throttles the Arm cores from 80 C, adds the GPU above 85, and the official line is that hitting the limit "is not harmful to the SoC". So the shape of the answer changed rather than the number: **measured that day on a Pi 4 at 1.8 GHz, HAT fitted and in a case, soaked, all thirty rows at full clock — 14.50x realtime at 192 kHz against the 3B+'s 4.25x, worst block 16% of a period against about half.** Throttling takes the clock down, not out, so a fully throttled Pi 4 is still faster than a 3B+ that was never throttled, and the 3B+ passed. Sizing against a reduced figure would be arithmetic with no decision hanging off it. **What does not change is the corollary: benchmark soaked, not cold** — that was the older row's best sentence and it is the reason the figures above are trustworthy. **What the thermal budget is actually about moved too**: not the SoC, which is unharmed at 85 C, but everything sharing the box with it, none of which is rated there — [#6](https://github.com/tamatebox/deck-pi/issues/6). |

### Operating systems considered and dropped

Recorded because "surely something leaner" gets re-derived.

**DietPi** is the near miss — same base, leaner — and loses because it inserts its
own configuration layer owning `config.txt`, a second actor mutating a load-bearing
file. Worth reconsidering at the stripped-image stage. **Ubuntu Server** has its
own firmware and overlay packaging where both vendors' instructions target
Raspberry Pi OS. **Alpine** has no systemd, which breaks the mount design outright.
**Arch ARM, Fedora, openSUSE** are mainline-kernel or thin on Pi 3. **moOde,
Volumio, piCorePlayer** are excluded *because* they already drive HiFiBerry and
claim bit-perfect — they **are** the player, so basing on one means fighting MPD for
exclusive `hw:` access. **Buildroot, Yocto, NixOS** are a possible destination for a
stripped image but only after the measurements: bring-up needs `alsacap`, `amixer`,
`dtoverlay -h`, `vcgencmd`, `rfkill`, `blkid` and `findmnt`, and a minimal image
strips all of them.

Three things the OS choice does **not** settle: whether the rootfs ends up
read-only, whether bring-up and production get separate images, and how the deck
starts at boot ([#8](https://github.com/tamatebox/deck-pi/issues/8)).
